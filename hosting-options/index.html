أين ينبغي أن يعيش Slaks؟

مقارنة عملية بين GitHub Pages وCloudflare Pages، مع فصل واضح بين الاستضافة الساكنة وخدمة Node/WebSocket وقاعدة البيانات التي تعمل في الخلفية.

مقارنة موثقةGitHub ActionsCloudflare Workersمناسبة للهاتف

الخلاصة الخاصة بمشروعك

النسخة الحالية من Slaks تعمل جيدًا على GitHub Pages لأنها موقع HTML/CSS/JavaScript مرتبط بمستودع GitHub وWorkflow للنشر. أما الـBackend الحقيقي، مثل WebSocket وMySQL، فهو خدمة منفصلة ولا ينبغي وضعه داخل GitHub Pages.

01التوصية الآن: أبقِ GitHub Pages للواجهة، واستخدم Worker أو نطاق Cloudflare لاحقًا عندما يصبح لديك نطاق مخصص وتحتاج تحكمًا مباشرًا في الترويسات.

GitHub Pages

GH
الأفضل للنسخة الحالية

استضافة ساكنة من المستودع مباشرة، ممتازة عندما تكون Git وPull Requests وGitHub Actions هي مركز العمل.

  • تاريخ وإصدارات وطلبات دمج في نفس المكان.
  • مناسبة لـHTML وCSS وJavaScript دون خادم.
  • يمكن استخدام نطاق مخصص وHTTPS.
  • لديك Workflow قائم يعيد بناء التقرير وينشر الموقع.

Cloudflare Pages

CF
الأفضل للمرحلة التالية

منصة نشر عالمية مع تحكم في الترويسات، نطاقات مخصصة، وامتداد إلى Pages Functions وWorkers.

  • ملف _headers لتحديد Cache-Control للأصول.
  • شبكة Cloudflare العالمية ونطاق pages.dev.
  • قرب طبيعي من Workers وKV وD1 وFunctions.
  • أنسب عندما يصبح الأداء الطرفي والتحكم في DNS أولوية.

المقارنة التفصيلية

الأرقام أدناه هي حدود وخيارات موثقة في المصادر الرسمية التي تمت مراجعتها في 2 نوفمبر 2026. قد تتغير الخطط مع الوقت.

المحورGitHub PagesCloudflare Pagesأثره على Slaks
نموذج الاستضافةملفات ساكنة من مستودع GitHub، مع إمكانية البناء عبر Actions.ملفات ساكنة موزعة عالميًا، مع إمكانية Pages Functions وWorkers.الواجهة الحالية تناسب الاثنين؛ الـBackend يبقى خدمة منفصلة أو ينتقل لاحقًا إلى Workers.
النشر والتكاملممتاز مع Git وPull Requests وGitHub Actions. Workflow المشروع يعيد توليد التقرير قبل النشر.يرتبط بمستودع Git أو يرفع مخرجات البناء عبر Wrangler.GitHub Pages يفوز الآن لأن خط النشر جاهز.
التخزين المؤقتالترويسات يديرها GitHub Pages. نستخدم بصمات v=HASH للأصول لتجاوز الكاش القديم.يمكن ضبط ترويسات الاستجابة عبر ملف _headers، مثل Cache-Control.Cloudflare أفضل للتحكم الكامل؛ الحل الحالي يعمل دون نقل الموقع.
النطاق المخصصمدعوم، مع إعداد DNS وHTTPS من إعدادات Pages.مدعوم؛ النطاق الفرعي يحتاج CNAME، والنطاق الأساسي يحتاج Zone وNameservers في Cloudflare.لا يمكن التحكم في elazzouz-dotcom.github.io داخل Cloudflare لأنه تابع لـGitHub.
الحدود المنشورةالموقع المنشور لا يتجاوز 1 GB، حد ناعم للنطاق 100 GB شهريًا، وحد ناعم 10 عمليات بناء في الساعة. Workflow Actions المخصص مستثنى من حد البناء المذكور.في الخطة المجانية: بناء واحد متزامن، 500 بناء شهريًا، 20,000 ملف، وحجم أصل منفرد 25 MiB.Slaks بعيد حاليًا عن هذه الحدود؛ عدد الملفات يجب مراقبته مع توسع شبكة 6600 عقدة.
الخادم وقاعدة البياناتلا يشغّل Node/WebSocket أو MySQL؛ يحتاج Backend خارجي.Functions وWorkers توفر منطقًا على الحافة، لكنها ليست بديلًا تلقائيًا لقاعدة MySQL الحالية.لا تنقل خدمة الجلسات الحالية دون تصميم هجرة منفصل.
الأمان والامتثالمناسب لمحتوى ساكن عام، لكنه ليس منصة معاملات حساسة أو SaaS تجاري بحسب قيود GitHub Pages.يوفر منظومة Cloudflare الأوسع، لكن قواعد الأمان والتكلفة تحتاج ضبطًا مستقلًا.افصل الأسرار والجلسات عن المستودع والواجهة في الحالتين.
أفضل استخدامموقع شخصي، وثائق، تجربة مفتوحة المصدر، لوحة ثابتة مرتبطة بمستودع.موقع عام يحتاج نطاقًا مخصصًا، Headers، Edge logic، أو Functions.المزيج المرحلي هو الأنسب: GitHub الآن، Cloudflare عند الحاجة.

خطة استضافة Slaks المقترحة

لا حاجة إلى نقل مفاجئ. يمكن إبقاء الواجهة مستقرة ثم إضافة طبقة Cloudflare عندما تملك نطاقًا مخصصًا.

الآن: GitHub Pages

بعد شراء النطاق

أضف النطاق إلى Cloudflare أو استخدم نطاقًا فرعيًا عبر CNAME، ثم اربطه بـCloudflare Pages أو Worker الكاش.
